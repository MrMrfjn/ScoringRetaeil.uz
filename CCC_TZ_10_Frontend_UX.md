# CCC — ТЗ 10: Продукт и UX — выделенный frontend, ролевые рабочие места, guided flows

---

## 0. Общий контекст

Сейчас весь UI живёт в `main.py` как Jinja-шаблоны (render_template_string). Это удобно для быстрой разработки, но ограничивает возможности интерактивности, клиентской фильтрации и масштабирования.

Данное ТЗ описывает **три больших направления** модернизации:

1. Выделение frontend-слоя (SPA).
2. Ролевые рабочие места (role-based workspaces).
3. Guided flows (мастера/визарды для типовых бизнес-сценариев).

Каждое направление разбито на этапы, задачи и подзадачи.

## 1. Выделенный frontend-слой (SPA)

### 1.1. Выбор технологии

- [ ] Определить стек:
  - [ ] **Рекомендация:** React (широкая экосистема) или Vue 3 (проще для команды, лёгкий старт).
  - [ ] Если команда маленькая и нужен минимальный бандл — рассмотреть Svelte.
  - [ ] Зафиксировать выбор и обосновать (размер команды, опыт, экосистема).

### 1.2. Архитектура

- [ ] Определить границу ответственности:
  - [ ] **Backend (Flask)** остаётся как:
    - API-сервер (все `/api/*` эндпоинты),
    - авторизация/сессия (или переход на JWT),
    - серверная логика (скоринг, импорт, ML).
  - [ ] **Frontend (SPA)** берёт на себя:
    - рендеринг всех дашбордов и аналитических страниц,
    - клиентская фильтрация, сортировка, агрегация (без перезагрузки страницы),
    - управление состоянием (фильтры, вкладки, тема).
- [ ] Определить способ авторизации:
  - [ ] Вариант A: сохранить cookie-сессию Flask, SPA делает fetch с credentials.
  - [ ] Вариант B: перейти на JWT (access + refresh token), SPA хранит в памяти/httpOnly cookie.
  - [ ] Зафиксировать выбор.
- [ ] Определить структуру проекта:
  - [ ] `CCC_scoringretail/` — backend (Flask API).
  - [ ] `CCC_scoringretail/frontend/` или `frontend/` — SPA-проект (npm/yarn).
  - [ ] Определить, как собранный SPA отдаётся:
    - [ ] Flask отдаёт `index.html` + статику из `build/dist`,
    - [ ] или отдельный nginx перед Flask.

### 1.3. Подготовка API

- [ ] Ревизия существующих API-эндпоинтов:
  - [ ] Составить список всех `/api/*` маршрутов (из `routes/api_routes.py` и `main.py`).
  - [ ] Для каждого определить:
    - [ ] формат ответа (уже JSON или нужно адаптировать),
    - [ ] нужна ли пагинация,
    - [ ] нужны ли дополнительные фильтры (branch, year, month, product, employee).
- [ ] Добавить недостающие API:
  - [ ] `GET /api/dashboard/kpi` — агрегированные KPI для главной (портфель, NPL, сбор%, просрочки).
  - [ ] `GET /api/portfolio/summary` — сводка портфеля с фильтрами.
  - [ ] `GET /api/intelligence/summary` — KPI + инсайты + рекомендации для аналитики.
  - [ ] `GET /api/employees/ranking` — рейтинг сотрудников (NPL, портфель, сбор).
  - [ ] `GET /api/segments/risk-matrix` — риск-матрица по возрастным группам / по доходу.
  - [ ] `GET /api/finance/opex` — расходы (когда появятся данные).
  - [ ] `GET /api/user/me` — текущий пользователь (роль, филиал, модули).
- [ ] Для каждого нового API:
  - [ ] определить параметры запроса,
  - [ ] формат ответа (JSON-схема),
  - [ ] ограничения по ролям.

### 1.4. Создание SPA-каркаса

- [ ] Инициализировать проект:
  - [ ] `npm create vite@latest frontend -- --template react-ts` (или vue-ts / svelte).
  - [ ] Установить зависимости:
    - [ ] маршрутизация (`react-router-dom` / `vue-router`),
    - [ ] состояние (`zustand` / `pinia` / встроенное),
    - [ ] HTTP-клиент (`fetch` обёртка или `axios`),
    - [ ] графики (`Chart.js` + обёртка или `recharts` / `echarts`),
    - [ ] UI-kit (опционально: `shadcn/ui`, `headlessui`, или свои компоненты).
- [ ] Настроить:
  - [ ] прокси на Flask API (в `vite.config` → `proxy`),
  - [ ] базовый layout (навбар, sidebar, content area),
  - [ ] тёмная/светлая тема (CSS variables + context/store).

### 1.5. Миграция дашбордов в SPA

- [ ] Поэтапный перенос (от простого к сложному):
  - [ ] **Этап 1:** Executive Dashboard (главная) — KPI-карточки + простые таблицы.
  - [ ] **Этап 2:** Portfolio — таблицы с drill-down, фильтры, сортировка.
  - [ ] **Этап 3:** Intelligence — полная аналитика (12 разделов).
  - [ ] **Этап 4:** Alerts — список алертов + детали.
  - [ ] **Этап 5:** Developer Portal — API-ключи, тест, документация.
  - [ ] **Этап 6:** Admin + Import/Export.
  - [ ] **Этап 7:** Finance/OPEX (новый раздел).
  - [ ] **Этап 8:** Scoring (форма + результат + печать).
- [ ] На каждом этапе:
  - [ ] реализовать компоненты,
  - [ ] подключить к API,
  - [ ] проверить авторизацию и RBAC,
  - [ ] визуальное QA.

### 1.6. Обратная совместимость

- [ ] Пока SPA не покрывает все страницы:
  - [ ] Flask продолжает отдавать старые Jinja-шаблоны для непортированных страниц.
  - [ ] В навбаре SPA — ссылки на ещё не портированные страницы ведут на Flask-версию.
- [ ] После полной миграции:
  - [ ] Flask отвечает только за API и отдачу `index.html`.
  - [ ] Старые шаблоны можно удалить.

## 2. UX для разных ролей (ролевые рабочие места)

### 2.1. Определение рабочих мест

- [ ] Определить **4 основных рабочих места** (workspace):

| Рабочее место | Роли | Стартовая страница | Ключевые виджеты |
|---------------|------|--------------------|------------------|
| **Директор** | `director`, `executive` | Executive Dashboard | KPI сети, EBITDA, NPL тренд, Decision Center, топ-филиалы, топ-риски |
| **Risk Director** | `risk_director`, `head_analyst` | Risk Intelligence | NPL центр, aging, хит-лист, risk matrix, vintage, AI predictions |
| **Branch Manager** | `branch_manager`, `credit_officer` | Branch Dashboard | KPI своего филиала, свои сотрудники, свои алерты, свой портфель |
| **Аналитик** | `analyst` | Analytics | Полная аналитика, сегменты, тренды, экспорт |

### 2.2. Стартовая страница по роли

- [ ] При логине определять роль пользователя и редиректить на его стартовую страницу:
  - [ ] Директор → `/` (executive dashboard).
  - [ ] Risk Director → `/intelligence`.
  - [ ] Branch Manager → `/?branch=<его_филиал>` (дашборд с предустановленным фильтром).
  - [ ] Аналитик → `/intelligence`.
- [ ] Реализация:
  - [ ] В SPA: после получения `/api/user/me` → роутер решает, куда перенаправить.
  - [ ] В Flask (пока SPA не готов): в `dashboard()` определять redirect на основе роли.

### 2.3. Настраиваемые виджеты

- [ ] Определить набор виджетов для каждого рабочего места:
  - [ ] **Виджет = компонент**, который:
    - подтягивает данные из конкретного API,
    - отображает карточку/таблицу/график,
    - может быть скрыт/показан пользователем (опционально).
  - [ ] Примеры виджетов:
    - `KPI_Portfolio` — портфель, выдачи, погашения.
    - `KPI_NPL` — NPL%, просрочка 30+/60+/90+.
    - `Table_Branches` — таблица филиалов с NPL и сбором.
    - `Table_Employees` — рейтинг сотрудников.
    - `Chart_NPL_Trend` — линейный график NPL по месяцам.
    - `List_Alerts` — последние алерты.
    - `List_Recommendations` — Decision Center.
    - `RiskMatrix_Age` — риск-матрица по возрасту.
    - `Vintage_Table` — когортный анализ.
- [ ] Для каждого рабочего места определить дефолтный набор и порядок виджетов.

### 2.4. Фильтры по роли

- [ ] Branch Manager:
  - [ ] Все данные автоматически фильтруются по его филиалу (из `/api/user/me`).
  - [ ] Фильтр «филиал» не показывается (или показывается заблокированным).
- [ ] Директор / Risk Director:
  - [ ] Полный доступ ко всем филиалам.
  - [ ] Фильтр «филиал» доступен, по умолчанию «Все».
- [ ] Аналитик:
  - [ ] Доступ ко всем данным на чтение.
  - [ ] Нет доступа к Admin, может не видеть некоторые действия (создание пользователей и т.п.).

### 2.5. Навигация по роли

- [ ] Навбар показывает только разделы, доступные текущей роли:
  - [ ] Сейчас это уже реализовано через `user.modules` в Jinja — перенести логику в SPA.
  - [ ] В SPA: получить `modules` из `/api/user/me`, на основе них строить навбар.
- [ ] Страницы, недоступные роли:
  - [ ] При прямом переходе по URL → редирект на стартовую или показ «Доступ запрещён».

## 3. Guided flows (мастера/визарды)

### 3.1. Определение сценариев

- [ ] Определить **3 основных мастера** на первом этапе:

| Мастер | Для кого | Описание | Шаги |
|--------|----------|----------|------|
| **«Запустить акцию»** | Директор, Branch Manager | Создание и запуск акционных условий: сниженная ставка / увеличенный лимит для сегмента/филиала | 1) Выбор филиала/сегмента → 2) Условия (ставка, лимит, срок) → 3) Прогноз влияния → 4) Подтверждение |
| **«Пересмотреть лимиты сегмента»** | Risk Director, Head Analyst | Изменение скоринговых порогов/лимитов для клиентского сегмента | 1) Выбор сегмента (по возрасту/доходу/региону) → 2) Текущие метрики (NPL, PD) → 3) Новые лимиты → 4) Оценка риска → 5) Применить |
| **«Закрутить скоринг в филиале»** | Risk Director, Директор | Ужесточение/ослабление скоринга в конкретном филиале | 1) Выбор филиала → 2) Текущее состояние (NPL, портфель, тренд) → 3) Параметры (мин. балл, макс. сумма, запрет продуктов) → 4) Подтверждение |

### 3.2. UX визарда

- [ ] Определить единый шаблон визарда:
  - [ ] **Шапка:** название мастера + индикатор шагов (1/4, 2/4…).
  - [ ] **Контент:** форма или информационный блок текущего шага.
  - [ ] **Подвал:** кнопки «Назад» / «Далее» / «Применить».
  - [ ] Визуально:
    - стеклянная панель на полный экран или модальное окно,
    - лёгкие переходы между шагами (slide или fade).

### 3.3. Реализация «Запустить акцию»

- [ ] **Шаг 1: Выбор филиала/сегмента**
  - [ ] Выпадающие списки:
    - филиал (из `/api/dashboard/kpi` или справочника),
    - сегмент клиентов (по возрасту, доходу).
  - [ ] Краткая сводка выбранного (кол-во договоров, NPL).
- [ ] **Шаг 2: Условия акции**
  - [ ] Поля:
    - новая ставка (% в месяц),
    - макс. сумма кредита,
    - срок действия акции (даты от–до).
  - [ ] Валидация (ставка в разумных пределах, даты не в прошлом).
- [ ] **Шаг 3: Прогноз влияния**
  - [ ] На основе текущих данных показать:
    - ожидаемое увеличение выдач,
    - ожидаемое изменение NPL (простая оценка: если ставка ниже → больше одобрений → возможно больше NPL).
  - [ ] На первом этапе — статичная формула или заглушка с пометкой «AI prediction — в разработке».
- [ ] **Шаг 4: Подтверждение**
  - [ ] Сводка: что, где, на каких условиях.
  - [ ] Кнопка «Применить» (сохраняет в БД, логирует в аудит).

### 3.4. Реализация «Пересмотреть лимиты сегмента»

- [ ] **Шаг 1: Выбор сегмента**
  - [ ] Выбрать тип сегментации: по возрасту / по доходу / по региону.
  - [ ] Выбрать конкретный сегмент из списка (например, «18–25» или «Пенсионеры»).
- [ ] **Шаг 2: Текущие метрики**
  - [ ] Отобразить:
    - кол-во договоров в сегменте,
    - NPL %,
    - средний чек,
    - текущий макс. лимит (если задан).
  - [ ] Данные из `/api/segments/risk-matrix` или аналогичного API.
- [ ] **Шаг 3: Новые лимиты**
  - [ ] Поля:
    - новый макс. лимит (сумма),
    - новый мин. балл скоринга для одобрения,
    - ограничение по сроку (макс. месяцев).
- [ ] **Шаг 4: Оценка риска**
  - [ ] Показать:
    - «при новых лимитах ~X% текущих заявок были бы отклонены/одобрены»,
    - или заглушку для будущей ML-оценки.
- [ ] **Шаг 5: Применить**
  - [ ] Сохранить правило в БД (новая таблица `segment_rules` или аналог).
  - [ ] Логировать в аудит.

### 3.5. Реализация «Закрутить скоринг в филиале»

- [ ] **Шаг 1: Выбор филиала**
  - [ ] Список филиалов с мини-KPI (NPL, портфель).
- [ ] **Шаг 2: Текущее состояние**
  - [ ] KPI филиала:
    - NPL %, тренд за 3 мес,
    - портфель, выдачи за месяц,
    - топ-3 рисковых сотрудника.
- [ ] **Шаг 3: Параметры ужесточения/ослабления**
  - [ ] Поля:
    - мин. балл скоринга для одобрения (ползунок или числовое поле),
    - макс. сумма одного договора,
    - запрет определённых продуктов (чекбоксы),
    - ограничение по сотрудникам (блокировка конкретных).
- [ ] **Шаг 4: Подтверждение**
  - [ ] Сводка изменений.
  - [ ] Кнопка «Применить» (сохранение + аудит).

### 3.6. Backend для визардов

- [ ] Определить новые API-эндпоинты:
  - [ ] `POST /api/wizard/promotion` — сохранить акцию.
  - [ ] `POST /api/wizard/segment-limits` — сохранить лимиты сегмента.
  - [ ] `POST /api/wizard/branch-scoring` — сохранить параметры скоринга филиала.
- [ ] Определить новые таблицы БД (если нужно):
  - [ ] `promotions` (филиал, сегмент, ставка, лимит, даты, created_by, created_at).
  - [ ] `segment_rules` (сегмент, макс_лимит, мин_балл, макс_срок, created_by, created_at).
  - [ ] `branch_scoring_rules` (филиал, мин_балл, макс_сумма, blocked_products, created_by, created_at).
- [ ] Все действия логировать в `audit_log`.

## 5. Ограничения и риски

- **Не ломать текущий продукт.** Пока SPA не покрывает страницу — Flask-версия остаётся рабочей.
- **Авторизация.** При переходе на SPA нужно чётко определить механизм сессии/токена. Не допускать ситуацию, когда пользователь не залогинен, а SPA показывает пустой экран без объяснения.
- **Данные для визардов.** «Прогноз влияния» в мастерах — на первом этапе заглушка; реальный ML-прогноз добавляется позже.
- **Объём работы.** Полная миграция на SPA — это **месяцы** работы. Начинать с самых ценных экранов (Executive Dashboard → Portfolio → Intelligence).
